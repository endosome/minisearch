# Phases 1 and 2: results

Phase 1 (safe fixes on existing APIs) and Phase 2 (single-execution search pipeline) of the performance spec, measured against the [WP-00 baseline](2026-10-15-wp00-baseline.md) on the same machine, corpus and toolchain. Decisions behind them: [ADR 0001](../../docs/adr/0001-performance-project-decisions.md).

Every change passed the whole `npm test` gate on its own before its commit. The gate covers the native tests and lints, the differential suite against MiniSearch, the upstream suite, the callback-trace suite and the size budget.

## How it was measured

`differential/ab.mjs`: two package builds on the 20,000-document bench corpus. Each round runs both packages in fresh processes, alternating which goes first, and takes the best of three passes (one for workloads that need a fresh index). Medians over rounds, with quartiles. Each workload's output checksum must match between the two builds, or the run fails.

Noise: on this machine a 39-query batch varies by about ±5% between runs (default search ranged 508–567 ms across runs of the same build). A change inside that band, with overlapping quartiles, is reported as no effect. Three apparent regressions (`searchJoined` +12%, dirty first pass +7.5%, stored-score search +3.5%, all from a 7-round run) were rerun with 15 rounds and came out at −0.5%, −1.8% and +0.7%.

## Phase 1

| Commit | Change (spec item) | Measured effect |
|---|---|---|
| `527d135` PR-002 | Build only the transfer fields a result consumes (WP-03) | Within noise on full-object batches (−2% to +0.6%). It removes a string per query plus one `"null"` per hit, which is invisible in 39-query batches of thousands of rows. |
| `5c0f430` PR-003 | Field boosts prepared once per query and borrowing field names; default search options borrowed (WP-03) | Within noise (`searchRaw` −8.6% in one run, overlapping quartiles) |
| `deb0f2a` PR-004 | O(1) `termCount` (WP-04) | **`termCount` 7.7–10× faster** (0.94–0.98 ms → 0.09–0.13 ms per 200 reads); boosted search, which reads it once per query, within noise |
| `4aa5cab` PR-005 | Borrowed boosted derived term; fuzzy cache keyed without allocating (WP-04) | Within noise |
| `4d80bfb` PR-006 | Row-tracking requirements (WP-02): match fields only with `includeMatch`; more than 64 fields take the fused path when they are not needed | **`search` with `includeMatch: false` −10.6%** (−15% against the baseline overall); others within noise |
| `27b5e5a` PR-008 | No needless copies in radix deletion, `keys()`, vacuum batches (WP-10) | Dirty first pass −5%, vacuum −2% (single run, within noise) |

Phase 1 overall against the baseline (7 rounds): `termCount` 0.13×, `includeMatch: false` 0.85×, everything else within noise. As the baseline profile predicted, plan and setup costs are under 2% of engine time with warm caches. The fixed-cost items save allocations per query rather than measurable batch time.

## Phase 2: WP-01 (`6b8d32e`)

One engine execution per public call where a stored field can replace the result score. Before, there were two for `search()` and `searchRaw()` and three for `searchJoined()`. The compact calls also stop scanning stored objects for a `score` when none can exist.

| Workload (A = Phase 1, B = WP-01, 9 rounds) | A ms | B ms | B/A |
|---|--:|--:|--:|
| `search` with a stored `score` field | 887.7 | 621.6 | **0.700** |
| `searchJoined` with a stored `score` | 625.4 | 545.2 | **0.872** |
| `searchRaw` with a stored `score` | 559.9 | 483.9 | **0.864** |
| `searchJoined` with a stored `title` (no scan) | 141.1 | 121.3 | **0.859** |
| `searchRaw` with a stored `title` (no scan) | 126.2 | 104.9 | **0.831** |
| `search` default | 542.0 | 567.1 | 1.046 (within noise) |
| `searchRaw`, `searchJoined`, `searchJoinedOpts` without stored fields | | | 0.97–0.99 |

Compatibility, by `differential/native_executions.mjs` and `callback_traces.mjs`:

- One execution for `search`, `searchJoined(Opts)`, `searchRaw` and `autoSuggest`, on clean and dirty indexes, with and without stored `score`. Two executions only after the caller adds a `score` to a live stored object. Rows are then reordered without being rebuilt, so getters still run once. The test fails on the baseline package.
- The two baseline divergences from MiniSearch are fixed: a stored `score` getter is read once per row, and `autoSuggest` follows a stored `score`. The trace suite has no known divergences left.

## WP-02 status

Done for the existing APIs: full rows track query terms always and match fields only with `includeMatch`, and the compact paths track neither. The rest of WP-02, the score-only and count-only requirements, waits for WP-13's new APIs (not scheduled: ADR 0001 names ordinary `search()` as the primary workload).
