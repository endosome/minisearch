# Phase 4: results, and the cumulative comparison with the baseline

Phase 4 of the performance spec covers ingestion, deletion, compaction and persistent memory: WP-08, WP-09, the rest of WP-10, WP-12 and WP-16. Same machine, corpora and method as the earlier reports ([baseline](2026-10-15-wp00-baseline.md), [Phases 1–2](2026-10-15-phase1-2.md), [Phase 3](2026-10-15-phase3.md)). Decisions and rejected experiments: [ADR 0003](../../docs/adr/0003-phase-4-decisions.md).

## Changes

| Commit | Change | Measured effect |
|---|---|---|
| `1461dab` WP-10 | Compaction remaps postings through a table indexed by old id (a hash map when ids are sparse), in one tree walk | discard 60% + vacuum + compact 0.791 (whole workload) |
| `394e769` | Wasm memory grows by an eighth of its size (1–64 MiB) per step: dlmalloc over a geometric system allocator | 1M documents × 4 fields: **357 s → 38 s** to index, linear. Dirty-index first pass **0.128**. `addAll` long text 0.873. |
| `a4c1b7d` WP-12 | New field and posting lists allocated for one entry | live memory −9.4% at 300k documents. Wasm memory at 1M: 1009 → 966 MiB. `addAll` long text 1.046. |
| `16e7981` WP-08 | No engine id maps for the facade's externally identified indexes; snapshot formats unchanged | live memory −12% at 300k (225.4 → 198.2 MiB). discard + vacuum 0.82, with compaction 0.74. `addAll` 0.96. |

### The `addAll` superlinearity, explained

The baseline matrix built 100k documents in 4.7 s and 1M in 200 s. A probe that adds the 1M × 4 corpus in 100k chunks found:

- Chunk times swung from 4 s to 142 s while the JS heap stayed flat (about 800 MiB).
- Collections freed nothing (239.5 → 239.5 MB, back to back) and mutator utilization fell to 0.13.

Each `memory.grow` replaces the module's `ArrayBuffer`, and V8 counts it as external memory. A bare `WebAssembly.Memory` grown a page at a time triggers a non-scavenge collection about every 10 grows, whatever the heap size.

std's dlmalloc grows by about one request. Ingestion therefore grew memory thousands of times, and each collection marked a JS heap that holds the corpus: O(N²). With geometric growth the same build takes 37.9 s (2.9–5.1 s per 100k).

The dirty-index first pass benefits the same way: its exact reruns allocate heavily (a 99 MiB peak in the baseline).

A first attempt kept std's allocator and allocated, then freed, a large block after each grow. It tripped a dlmalloc assertion on `loadNativeJSON` and was discarded before commit.

### Measured and not merged

All in ADR 0003 and ADR 0002:

- WP-09 per-document term aggregation: `addAll` 1.13–1.32. A hash lookup replaces a radix lookup of about the same cost.
- Trimming posting lists' growth room during indexing: fragmentation, Wasm memory 497 against 276 MiB at 300k.
- `field_present` bit-packing: 0.4% of memory.
- Inline singleton postings: under 2%; deferred.
- WP-16 snapshot-only id remap: deferred. The facade compacts after vacuums. The 16M-slot snapshot limit (`next_id × fields`) also binds live documents and needs a format version, not a remap.

## Cumulative: baseline against the end of Phase 4

`target/pkg-baseline` (`1514d7b`) against `target/pkg-wp08` (`16e7981`), all workloads on the 20,000-document corpus, 7 rounds. Raw samples: [`2026-10-15-cumulative-ab.json`](2026-10-15-cumulative-ab.json).

At 1M documents × 4 fields, indexing went from 200 s (baseline matrix) or 357 s (Phase 3 probe) to 38 s. Wasm memory after indexing went from 1186 MiB in the baseline matrix to 966 MiB, measured before WP-08, which saves another 12% of live memory at 300k documents.

The compact calls (`searchRaw`, `searchJoined`, `autoSuggest`) were engine-bound in the baseline and stay within a few percent. Their time is posting traversal, which no merged change made cheaper; WP-06's attempt is in ADR 0002. No workload is slower than the baseline.
