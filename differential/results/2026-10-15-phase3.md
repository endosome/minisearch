# Phase 3: results

Phase 3 of the performance spec (memory and hot-path work for the primary workload, ordinary `search()`), measured on the same machine, corpus and toolchain as the [WP-00 baseline](2026-10-15-wp00-baseline.md) and the [Phases 1–2 report](2026-10-15-phase1-2.md). Rejected and deferred items (WP-05, WP-06, WP-11) are in [ADR 0002](../../docs/adr/0002-rejected-and-deferred-phase-3-items.md).

Every change passed the full `npm test` gate on its own before its commit. Method and noise band (about ±5% per batch) as in the Phases 1–2 report.

## Changes

| Commit | Change | Measured effect (B/A, 9 rounds, against the previous step) |
|---|---|---|
| `93d9450` WP-07 | Per-document `DocSlot` (56 bytes of per-query scalars together) plus per-row buffers for derived terms, match fields and query slots, handed out in touch order and reused across queries. Each hit carries its row index. | exact `search` 0.90, default 0.95, `autoSuggest` 0.90, `searchJoinedOpts` exact 0.87, compact calls neutral. Retained scratch at 100k documents: 1 field 12.1 → 7.0 MiB, 4 fields 18.6 → 17.7 MiB. |
| `60edd54` | JS row building: `terms`, `queryTerms`, each match field list and the result array allocated at their final length and filled by index. Rows, order and objects are unchanged. | default `search` 0.52, `includeMatch: false` 0.63, stored-score search 0.69, `boostDocument` 0.71, OR and filter 0.81, exact 0.84 |
| `e799598` | Full rows for any field count: a term's field set takes one (spec, mask) word per 64 fields, with an explicit single-word path. The >64-field map-path fallback is deleted. | 2-field corpus within noise. 100k × 65 fields, `search()` p50 against the baseline: 0.33–0.49 by query shape. |

Earlier versions of WP-07 cost the compact calls 7–16%: the row was loaded on every posting, and the row struct was 72 bytes. Loading the row lazily, carrying its index in the hit, and splitting rows into parallel buffers removed that cost.

The JS row change was chosen with a micro-benchmark on captured engine transfers (39 queries, 222,920 rows, outputs deep-equal). Preallocation alone measured 0.52× push(); cached field-list templates 0.92×, not adopted.

The ordinary `search()` workload, the primary one in ADR 0001, is 0.55× Phase 2. Against the baseline it is about 0.6×. The baseline measured 508–567 ms in separate runs of the same workload, against 323 ms here. A cumulative A/B against the baseline package comes with the Phase 4 report. The compact calls were already engine-bound; they gain only where they share the engine's row state.

**`addAll` 1.068 is a measurement artifact.** In the full run, `addAll` runs in the same process after twenty search workloads. Run alone, no Phase 3 step changes it: 9 rounds each, WP-01 → WP-07 0.994, → JS rows 1.001, → wide masks 0.986. A fresh build of `e799598` measured 1.000 against the frozen package. The difference comes from the JS heap state left by the earlier workloads, not from indexing code.

## Rejected after measurement in this phase

- WP-06 tombstone-free slice walk: 4–20% slower (duplicated loop body), or within noise (single loop). See ADR 0002.
- WP-05 indexed field lookup: nothing to win (about 650 lookups against 240k postings at 65 fields).
- WP-11 cold traversal: 1.3% of engine time; deferred until a multilingual or extreme-distance workload exists.
